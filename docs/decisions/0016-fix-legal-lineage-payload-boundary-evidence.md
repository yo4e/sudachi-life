# ADR 0016: Fix legal Protocol-v1 evidence for the 64 KiB lineage limit

- Status: Accepted
- Date: 2026-07-27
- Decision authority: project-owner routine clarification delegation
- Implementation issue: #61
- Clarification issue: #112

## Context

P2-J09 requires exact evidence at the 64 KiB current-lineage logical-payload boundary and one byte over.

Later accepted Protocol-v1 clarifications close every request and package field:

- at most four requests and four successful packages per current lineage;
- no optional request context or filler;
- exact three-field provenance;
- zero or one fixed-shape proposal;
- no free text, opaque payload, padding, repeated collection, or arbitrary integer inflation;
- 16 KiB request and package values are hard ceilings rather than targets.

The legal maximum generated by four complete closed-v1 cycles is therefore structurally below 64 KiB. A canonical 64 KiB or 64 KiB-plus-one epoch cannot be constructed without undeclared filler, forged packages, direct consultation-row mutation, or a new protocol version.

The existing ingress runtime nevertheless enforces the exact arithmetic guard over independently measured request and successful package bytes. The evidence map must distinguish that exact arithmetic boundary from the smaller reachable Protocol-v1 maximum.

This is a routine clarification under `docs/phase2/CLARIFICATION_DELEGATION.md`. It retains the 64 KiB limit and one-over rejection while forbidding fake canonical history.

## Decision

### 1. Exact pure accounting function

Define one pure protected function over three nonnegative integer byte counts:

```text
projected_lineage_payload_bytes = current_request_bytes
                                + current_success_package_bytes
                                + candidate_success_package_bytes
```

The function:

- admits projected value `65536`;
- rejects projected value `65537` with the existing typed ingress logical-payload failure;
- rejects booleans, negative integers, floats, strings, nulls, and unsupported units;
- performs ordinary exact integer addition with no wrapping or alternate unit conversion;
- creates no canonical row, event, package, artifact, clock read, or organism history.

The ingress runtime must use this same function after independently measuring:

- the sum of current-lineage request `canonical_size_bytes`;
- the sum of current-lineage successful ingress-receipt `measured_package_bytes`;
- the candidate exact canonical package byte length.

### 2. Exact legal end-to-end maximum

A separate legitimate four-cycle fixture measures the reachable Protocol-v1 maximum. It must:

- use the maximum-length legal organism identifier;
- create four legal ADR 0014 request envelopes through public garden wakes;
- use the largest exact valid package shape among the declared deterministic fixture cases for each successful ingress;
- finalize each proposal through the explicit disposition wake;
- use ordinary garden state transitions to preserve eligibility and avoid manufactured maintenance state;
- independently sum stored request canonical sizes plus successful receipt measured bytes;
- prove the exact legal epoch total is less than `65536`;
- prove response, proposal, provenance, receipt, completion, event, disposition, and other metadata are not double-counted;
- prove a fifth request or charge cannot increase the epoch because finite request/charge limits apply first;
- preserve every inherited physical ceiling and the next-wake reserve.

The phrase “largest exact valid package shape” means the largest canonical byte length actually produced by the closed declared fixture cases for the same legal request shape. It does not authorize altering fixture schemas or adding padding.

### 3. New lineage epoch

After accepted rollback:

- the new current lineage starts with zero request and successful-package logical bytes;
- old-lineage request and receipt bytes remain immutable historical evidence;
- old-lineage bytes are excluded from current-lineage accounting;
- the pure accounting guard applies independently to the new epoch.

### 4. No fake one-over

No protected test may create a 65537-byte canonical lineage through:

- filler or context fields;
- forged external packages;
- direct consultation-row/event mutation;
- repeated metadata or double counting;
- inflated identifiers or integers outside the accepted structural fixtures;
- altered request/package/provenance cardinality.

The one-over evidence belongs to the pure accounting function. End-to-end evidence proves the exact reachable maximum and proves that runtime accounting uses independently measured canonical bytes.

## Superseded text

This ADR supersedes only P2-J09's implication that closed Protocol v1 can legally populate canonical state exactly at 64 KiB and one byte over. The 64 KiB hard limit, exact arithmetic boundary, one-over rejection, per-lineage epoch, and all other logical-payload rules remain normative.

## Consequences

- Slice 42 can prove the exact 64 KiB guard without manufacturing invalid canonical history.
- The legal four-cycle maximum becomes a measured protected fact rather than an assumed 64 KiB filler scenario.
- Rollback lineage filtering remains independently testable.
- No request/package schema or finite limit changes.
- All original 152 Phase 1 tests remain unchanged and passing.
