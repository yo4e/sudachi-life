# ADR 0014: Fix the largest structural request parent cardinality

- Status: Accepted
- Date: 2026-07-27
- Decision authority: project-owner routine clarification delegation
- Implementation issue: #61
- Clarification issue: #109

## Context

ADR 0010 closes Protocol v1 request fields and defines P2-E10's largest structural request without optional context or filler. Its example requires the full sixteen current-lifecycle parent events.

The frozen Phase 1 garden wake and the accepted optional request-extension insertion point make that cardinality impossible for the only eligible request path.

A request is considered only after an incomplete-objective `no_applicable_action` result. The public lifecycle wrapper invokes `maybe_create_fixture_request` immediately before the frozen `checkpoint_pending` event is appended. `phase2_request_impl.py` includes every event already written in the considering lifecycle as `parent_event_sequences`.

The exact eligible core has eight existing events before the request child is created:

1. `wake_accepted`;
2. `input_claimed`;
3. `observation_created`;
4. `action_abstained`;
5. `evaluation_completed`;
6. `failure_streak_updated`;
7. `lifecycle_completed`;
8. `budget_ledger`.

`consultation_request_created` is the child and cannot parent itself. `checkpoint_pending` is appended after the optional request extension and cannot be a request parent.

Requiring sixteen parents would require private event manufacture or a change to the frozen Phase 1 wake. Both are forbidden.

This is a routine clarification under `docs/phase2/CLARIFICATION_DELEGATION.md`: it replaces one impossible cardinality example with the exact cardinality generated by the already accepted implementation boundary. It changes no research purpose, contract intent, authority, security boundary, Phase 1 behavior, schema, budget, permission, or external capability.

## Decision

### 1. Exact largest structural request

For Protocol v1, the largest structural request is the largest request emitted by the only eligible incomplete-objective `no_applicable_action` path.

It contains exactly the eight current-lifecycle core parent event sequences listed above.

The parent array must be:

- sorted in ascending event-sequence order;
- unique;
- same-organism;
- same current lineage;
- same considering lifecycle;
- composed only of existing events;
- entirely earlier than the request event.

The exact eight parent event types, in sequence order, are:

```text
wake_accepted
input_claimed
observation_created
action_abstained
evaluation_completed
failure_streak_updated
lifecycle_completed
budget_ledger
```

The request event itself and the later `checkpoint_pending` event are excluded.

### 2. Other P2-E10 dimensions remain unchanged

The largest structural request also uses:

- the maximum-length legal organism identifier accepted by the protected identifier grammar;
- current-lineage request ordinal four;
- every protected declared action ID in exact order;
- every derived permission ID in exact order;
- every requested proposal type in exact order;
- the complete closed Protocol-v1 request envelope field set;
- the exact pre-creation budget snapshot;
- expiry equal to considering lifecycle plus two;
- exact organism authority and request source;
- independently recomputed observation and objective digests;
- independently recomputed request identity, ID, final canonical bytes, and stored size.

No context, filler, padding, free text, opaque data, repeated collection, undeclared field, or artificial integer inflation is permitted.

The 16 KiB request limit remains a hard ceiling, not a target.

### 3. Physical evidence remains required

The legal ordinal-four largest structural request and its ordinary checkpoint must preserve:

- 8 MiB active database and individual database-artifact ceilings;
- 40 MiB checkpoint-store ceiling;
- 64 MiB runtime working-set ceiling;
- 1 MiB next-wake active-database reserve;
- real SQLite sidecar and checkpoint-staging accounting.

The request must be produced through legitimate earlier request, terminalization or ingress/disposition, and ordinary garden transitions. Tests may not insert consultation rows, events, ordinals, charges, or lifecycle state directly.

## Superseded text

This ADR supersedes only:

- ADR 0010 section 4's statement that the largest structural request has sixteen current-lifecycle parents;
- `docs/phase2/ADR0010_TEST_MATRIX_AMENDMENT.md` row P2-E10 to the extent of that parent cardinality;
- any matching P2-E10 prose that treats sixteen parents as reachable by the accepted request path.

Every other ADR 0010 request rule and the 16 KiB ceiling remain normative.

## Consequences

- Slice 42 may construct the legal largest structural request without private canonical mutation.
- The frozen Phase 1 wake and accepted request insertion point remain unchanged.
- Parent ancestry becomes an exact property of the only eligible request path rather than a hypothetical upper bound.
- Missing, extra, reordered, future, cross-lineage, cross-lifecycle, or wrong-type parent evidence must fail protected tests.
- All original 152 Phase 1 tests remain unchanged and passing.
- Any future request work class or alternate parent cardinality requires a later reviewed protocol version or ADR.
